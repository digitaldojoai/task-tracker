# Reflection

I used Claude Code as the AI tool for essentially this entire project: reading the course brief and my existing repo, planning the two features, writing all the backend and frontend code, running the server, driving a real browser to click through the app, running pytest, and writing this documentation. I'm not a programmer, so I relied on it to make the concrete implementation decisions (how to model an "overdue" flag, how to validate a tag) while I set the direction and reviewed what came back before accepting it.

The moment it helped most was right at the start, before any feature code was written. I assumed my `task-tracker` folder already had a working app from Modules 1-3, since that's what the assignment brief assumes you're extending. Claude actually opened the folder and compared it against the brief instead of taking my assumption at face value, and found that only the Module 1 skeleton existed — no frontend, no working update/delete, no git repo, no real tests. That completely changed the plan: instead of jumping straight into "due dates" and "tags," it had to first finish the baseline the assignment assumed was already there. Catching that early saved the whole project from being built on a foundation that didn't match what I described.

The moment it slowed things down was the opposite kind of surprise, later on: the delete button silently did nothing when actually clicked in the browser, even though the code read correctly. It turned out the native `confirm()` dialog gets suppressed in the test browser, so it always returned false. That was only visible by actually running the app and checking the browser console — reading the code alone wouldn't have caught it. It cost a round trip to diagnose and rewrite as an inline "click again to confirm" button.
The place my review changed the result was the overdue rule. Claude's first version marked anything with a past due date as overdue, full stop. When I looked at that logic, it didn't feel right — a task I already finished shouldn't be flagged as overdue just because I closed it out late. We corrected it so a task is only overdue if it isn't already `Done`, and added a test specifically to pin that behavior down. Small catch, but it's the kind of thing that's obvious once you think about how you'd actually use the feature, and easy to miss if you just accept the first version.

The revision round taught the same lesson from the other side. Feedback showed that an explicit `null` title in an update was accepted and stored. Both the AI and I had read `Optional[str] = None` as "optional field," when it actually collapses two different requests — *omitted* and *explicitly null* — into one value. My instinct was to ask for "a fix," which would have patched only `title`; asking instead for the cause, and whether the same hole existed elsewhere, surfaced a second defect in the storage layer writing merged values without validating them at all.
